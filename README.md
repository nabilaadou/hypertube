# Hypertube

The Spring Boot API lives in `server/`. The Next.js app lives in `client/`.

## Run with Docker

Install Docker with Compose 2.24 or newer and Make. From the repository root, copy the Docker environment template.

```sh
cp .env.example .env
```

Set `POSTGRES_PASSWORD` to a local password in `.env`. Generate the three auth secrets and set their values in `.env` as well.

```sh
openssl rand -hex 64  # AUTH_SESSION_SECRET
openssl rand -hex 32  # AUTH_HANDOFF_SECRET
openssl rand -base64 32  # AUTH_JWT_SECRET
```

Start the development stack.

```sh
make up
```

Open `http://localhost:3000`. The API is available at `http://localhost:8080/api/health`, and the auth provider page is at `http://localhost:4567`. `make up` starts PostgreSQL, Spring Boot, Next.js, and the auth service together. Compose reloads Next.js when you edit the frontend and restarts Spring Boot when you edit backend source files. Changes to dependency manifests rebuild the corresponding image.

PostgreSQL is available at `localhost:5432` from the host and `postgres:5432` from other services. The database, user, and password come from the root `.env` when the database volume is first initialized.

Compose reads service settings from the root `.env`. If you already have one, add any missing settings from `.env.example`. To change a host port, edit `HYPERTUBE_CLIENT_PORT`, `HYPERTUBE_SERVER_PORT`, `HYPERTUBE_AUTH_PORT`, or `HYPERTUBE_POSTGRES_PORT` in `.env` and restart `make up`. For example, `HYPERTUBE_CLIENT_PORT=3100` serves the frontend at `http://localhost:3100`.

Press Ctrl+C to stop the services. Run `make down` to remove the containers and network while keeping PostgreSQL data. Run `make clean` to also delete the database volume, orphaned project containers, and images built for Hypertube.

## Run without Docker

Install JDK 21 or newer, Maven 3.9 or newer, Node.js 24 or newer, and npm.

From the repository root, copy the local configuration template.

```sh
cp client/.env.example client/.env
```

Set `BACKEND_URL=http://localhost:8080` in `client/.env`. Next.js reads this value on the server. Keep local credentials in ignored `.env` files and commit only variable names and placeholders in `.env.example`.

Start the API in one terminal.

```sh
cd server
POSTGRES_PASSWORD=your-local-postgres-password mvn spring-boot:run
```

Use a running PostgreSQL instance and set `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, or `POSTGRES_USER` if your connection differs from `localhost:5432`, database `hypertube`, user `hypertube`.

Flyway owns the database schema. Write schema changes as SQL migrations in `server/src/main/resources/db/migration`, using the next version and a description, such as `V7__add_user_preferences.sql`. Define tables, constraints, indexes, and database defaults in these files. Commit each migration with the corresponding Java entity mapping changes. Once a migration has been applied, leave it unchanged and add a new version for further changes.

Spring Boot runs Flyway automatically on startup, applies pending migrations in version order, and tracks their versions and checksums in `flyway_schema_history`. Hibernate then validates the resulting schema with `spring.jpa.hibernate.ddl-auto=validate`; it does not create or update tables. Entity annotations describe how Java fields map to the database, including values generated by the database.

Start Next.js in a second terminal.

```sh
cd client
npm ci
npm run dev
```

Open `http://localhost:3000`. The home page reports whether it can reach the API at `GET /api/health`. If `BACKEND_URL` is missing or invalid, the page tells you how to configure it. Restart Next.js after changing `client/.env`.

## Test 42 and Google sign-in

Use the root `.env` from the Docker setup above. If you have an existing `auth-server/.env`, move its values for `AUTH_BASE_URL`, `AUTH_SESSION_SECRET`, and the provider credentials into the root `.env`.

Add the client ID and secret for each provider you want to test to `.env`. You can configure either provider on its own. The auth service starts with `make up`; providers without credentials are shown as unconfigured on the sign-in page.

Register the redirect URIs with your 42 application and Google **Web application** OAuth client. These are the URIs for the ports in `.env.example`. If Google OAuth is in testing mode, add the Google account you plan to use as a test user.

| Provider | Redirect URI |
| --- | --- |
| 42 | `http://localhost:4567/auth/marvin/callback` |
| Google | `http://localhost:4567/auth/google_oauth2/callback` |

```sh
make up
```

Open `http://localhost:4567` and select a provider. After a successful callback, the auth service creates a handoff through `POST /internal/auth/login-handoffs`. Handoffs expire after two minutes. The browser submits the handoff to `POST /api/auth/login-handoffs/complete`, which saves or updates the user in PostgreSQL, issues a signed JWT access token and a refresh token, and returns the access token, token lifetime, and user profile as JSON. The profile contains the database ID, provider, provider user ID, and available name and email. Repeat sign-ins with the same provider account reuse the database ID.

Run `make up` again after changing `.env`. Use the same browser-facing hostname and scheme in `AUTH_BASE_URL` and `SPRING_PUBLIC_URL` so the browser can carry the login cookie to Spring Boot.

## Backend JWT authentication

Handoff completion creates a `user_sessions` row for refresh and logout and returns this JSON shape:

```json
{
  "accessToken": "<signed JWT>",
  "tokenType": "Bearer",
  "expiresIn": 600,
  "expiresAt": "<UTC timestamp>",
  "user": { "id": 1, "provider": "google", "providerUserId": "...", "displayName": "...", "email": "..." }
}
```

Send the access token as `Authorization: Bearer <accessToken>`. Access cookies are ignored and old access cookies are deleted when issuing new credentials. JWTs use HS256 with a dedicated signing key for this single-service backend. They contain `sub`, `sid`, `jti`, `iat`, `exp`, issuer, audience, and access-token type. Signature, algorithm, type, timestamps, issuer, audience, and identifiers are validated. There is no servlet `HttpSession` or `JSESSIONID`.

Refresh credentials are random 256-bit Base64URL strings. Only SHA-256 hashes are stored in PostgreSQL. The `hypertube_refresh` cookie is HttpOnly, host-only, `SameSite=Strict`, and scoped to `/api/auth`. Secure cookies are enabled by default. The local `.env.example` explicitly sets `AUTH_COOKIE_SECURE=false` for HTTP development; use `true` with HTTPS. Keep `AUTH_JWT_SECRET` stable across restarts and shared by backend instances. Generate at least 32 random bytes with `openssl rand -base64 32`. `AUTH_JWT_ISSUER` defaults to `hypertube` and `AUTH_JWT_AUDIENCE` to `hypertube-api`. The Ruby provider service continues to use its separate `AUTH_SESSION_SECRET`.

| Endpoint | Behavior |
| --- | --- |
| `POST /api/auth/login-handoffs/complete` | Consumes the browser proof and handoff, saves the user, creates an authentication session, and returns access JSON plus the refresh cookie in one transaction. |
| `GET /api/auth/me` | Returns the user profile for the Bearer token. |
| `GET /api/auth/csrf` | Sets `XSRF-TOKEN` and returns its `headerName` and `token`. |
| `POST /api/auth/refresh` | Uses the refresh cookie without requiring a valid access token, rotates refresh credentials, and returns a new access token. |
| `POST /api/auth/logout` | Revokes only the current session and clears its refresh cookie; returns `204` even when already signed out. A valid Bearer token's `sid` takes precedence over a mismatched cookie. |

For refresh and logout, retain the cookie from `GET /api/auth/csrf` and send the response's `token` in the `X-XSRF-TOKEN` header. Missing or invalid CSRF headers return `403`; form parameters are not accepted for these cookie endpoints. Other protected API requests use the explicit Bearer header. The health endpoint remains public. Authentication failures use centralized Problem Detail responses; invalid refresh credentials return `401` and clear the refresh cookie.

Access lasts `AUTH_ACCESS_TTL` (default `10m`). Refresh sessions have a sliding idle deadline of `AUTH_SLIDING_TTL` (default `7d`) and a hard deadline of `AUTH_ABSOLUTE_TTL` (default `30d`) from login. Each successful rotation advances the idle deadline to the earlier of now plus seven days or the hard deadline. The hard deadline never moves. JWT expiry is also capped by those deadlines. The refresh cookie has its own lifetime, so it still reaches the refresh endpoint after access expiry.

Refresh rotation locks the session pessimistically. The previous hash is retained with an `AUTH_REFRESH_GRACE` window (default and maximum `5s`). A duplicate inside this window receives an access JWT without a refresh `Set-Cookie` header; it does not rotate again or extend the window. This prevents out-of-order responses from overwriting the winning cookie without storing recoverable refresh tokens. Hashed history retains each consumed token's original deadline, including overlapping rotations. Reusing a consumed token outside its window revokes that session. Ordinary rotation leaves already-issued JWTs valid until their ten-minute expiry; revocation or logout invalidates all JWTs with that `sid` immediately through a session denylist.

Refresh and logout serialize on the session row. Session storage contains only the user/session IDs, refresh hashes and grace deadline, expiry deadlines, and revocation flag.

A scheduled cleanup runs every `AUTH_CLEANUP_INTERVAL` (default `PT15M`). Each run removes up to 1,000 expired/revoked sessions and 1,000 expired revocation records using `SKIP LOCKED`; consumed-token history cascades with its session. Revocation tombstones remain until the immutable hard deadline so deleting a revoked session cannot make its JWTs valid again.

Flyway migrations preserve existing users and refresh credentials. V6 removes device/IP metadata and unused audit timestamps while retaining session IDs, token hashes, expiry, and revocation state. Applied migrations remain unchanged, and Hibernate validates the resulting schema.

## Verify changes

From the repository root, run the API smoke test and check the frontend.

```sh
(cd server && mvn verify)
(cd client && npm ci && npm run lint && npm run build)
```

The JWT and refresh integration tests run when `TEST_DATABASE_URL` is set. They reset the users, handoffs, and revocation tables between cases and use a controllable clock for expiry tests. Start a disposable PostgreSQL database:

```sh
docker run --rm -d --name hypertube-session-tests -e POSTGRES_PASSWORD=session-tests -p 127.0.0.1:55432:5432 postgres:17-alpine
```

Once it is ready, run the backend suite and remove the test container:

```sh
(cd server && TEST_DATABASE_URL=jdbc:postgresql://localhost:55432/postgres TEST_DATABASE_PASSWORD=session-tests mvn verify)
docker stop hypertube-session-tests
```

`TEST_DATABASE_USER` defaults to `postgres`. Without `TEST_DATABASE_URL`, the PostgreSQL integration tests are skipped and the controller/security tests still run.

With both apps running, `curl -fsS http://localhost:8080/api/health` should return `{"status":"UP"}` and the home page should show “API is online.” To check the configuration diagnostic, clear `BACKEND_URL` in the `.env` used to start the client, restart it, and reload the page.
