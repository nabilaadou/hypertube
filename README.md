# Hypertube

The Spring Boot API lives in `server/`. The Next.js app lives in `client/`.

## Run with Docker

Install Docker with Compose 2.24 or newer and Make. From the repository root, copy the Docker environment template.

```sh
cp .env.example .env
```

Set `POSTGRES_PASSWORD` to a local password in `.env`. Generate the three auth secrets and set their values in `.env` as well.

```sh
openssl rand -hex 64  # AUTH_SESSION_SECRET
openssl rand -hex 32  # AUTH_HANDOFF_SECRET
openssl rand -base64 32  # AUTH_JWT_SECRET
```

Start the development stack.

```sh
make up
```

Open `http://localhost:3000`. The API health check is at `http://localhost:8080/api/health`, and the OAuth service listens at `http://localhost:4567`. `make up` starts PostgreSQL, Spring Boot, Next.js, and the auth service together. Compose reloads Next.js when you edit the frontend and restarts Spring Boot when you edit backend source files. Changes to dependency manifests rebuild the corresponding image.

The `assets` service downloads the landing page media from the public R2 bucket before the client starts. The service verifies each file against its SHA-256 hash and stores it in Docker volumes. Later starts reuse verified files. If a download fails or a checksum differs, the client waits until the asset is available and a subsequent start succeeds.

PostgreSQL is available at `localhost:5432` from the host and `postgres:5432` from other services. The database, user, and password come from the root `.env` when the database volume is first initialized.

Compose reads service settings from the root `.env`. If you already have one, add any missing settings from `.env.example`. To change a host port, edit `HYPERTUBE_CLIENT_PORT`, `HYPERTUBE_SERVER_PORT`, `HYPERTUBE_AUTH_PORT`, or `HYPERTUBE_POSTGRES_PORT` in `.env` and restart `make up`. For example, `HYPERTUBE_CLIENT_PORT=3100` serves the frontend at `http://localhost:3100`.

Press Ctrl+C to stop the services. Run `make down` to remove the containers and network while keeping PostgreSQL data and downloaded assets. Run `make clean` to also delete the database and asset volumes, orphaned project containers, and images built for Hypertube.

## Run without Docker

Install JDK 21 or newer, Maven 3.9 or newer, Node.js 24 or newer, and npm.

Start the API in one terminal.

```sh
cd server
POSTGRES_PASSWORD=your-local-postgres-password mvn spring-boot:run
```

Use a running PostgreSQL instance and set `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, or `POSTGRES_USER` if your connection differs from `localhost:5432`, database `hypertube`, user `hypertube`.

Flyway owns the database schema. Write schema changes as SQL migrations in `server/src/main/resources/db/migration`, using the next version and a description, such as `V8__add_user_preferences.sql`. Define tables, constraints, indexes, and database defaults in these files. Commit each migration with the corresponding Java entity mapping changes. Once a migration has been applied, leave it unchanged and add a new version for further changes.

Spring Boot runs Flyway automatically on startup, applies pending migrations in version order, and tracks their versions and checksums in `flyway_schema_history`. Hibernate then validates the resulting schema with `spring.jpa.hibernate.ddl-auto=validate`; it does not create or update tables. Entity annotations describe how Java fields map to the database, including values generated by the database.

Start Next.js in a second terminal.

```sh
cd client
npm ci
npm run prepare:media
npm run dev
```

Open `http://localhost:3000` to view the landing page.

## Prepare the landing page media

Docker downloads the files from R2 into persistent volumes. To run without Docker, run `npm run prepare:media` from `client/`. It copies the tracked theater GLB from `models/` to `client/public/models/`. It also copies `reel.mp4`, `reel-poster.jpg`, and `theater.png` from the local `design-assets/` folder to `client/public/media/` when available.

The public copies are ignored by Git. A fresh clone includes the theater model. Supply the movie edit and preview images locally in `design-assets/`, then rerun the command. Missing source files produce a message and leave any existing public copy available. The video preview displays an unavailable message when the edit cannot load.

The media script prefers `design-assets/reel-with-sound.mp4` when present. To prepare it from the supplied two-track reel, run this command from the repository root with FFmpeg installed.

```sh
ffmpeg -i design-assets/reel.mp4 -map 0:v:0 -map 0:a:1 -c copy -movflags +faststart design-assets/reel-with-sound.mp4
(cd client && npm run prepare:media)
```

The command copies the original video and its audible second audio track. For a reel that already has a single audible track, supply it as `design-assets/reel.mp4`.

The served model URL is `/models/private-home-cinema-textured.glb`. The edit and image URLs begin with `/media/`. The media paths and poster lineup are in `client/app/data/movies.ts`.

The public R2 bucket must contain these objects. The setup checks their hashes against the manifest in `client/scripts/fetch-assets.mjs`.

| R2 object | Local source |
| --- | --- |
| `media/reel.mp4` | `design-assets/reel-with-sound.mp4` |
| `media/reel-poster.jpg` | `design-assets/reel-poster.jpg` |
| `media/theater.png` | `design-assets/theater.png` |
| `models/private-home-cinema-textured.glb` | `models/private-home-cinema-textured.glb` |

To change the bucket, set `ASSET_BASE_URL` in the root `.env`. To update an asset, upload the replacement and update its SHA-256 hash in the manifest in the same change.

## Test 42 and Google sign-in

Use the root `.env` from the Docker setup above. If you have an existing `auth-server/.env`, move its values for `AUTH_BASE_URL`, `AUTH_SESSION_SECRET`, and the provider credentials into the root `.env`.

Add the client ID and secret for each provider you want to test to `.env`. You can configure either provider on its own. The auth service starts with `make up` and returns its enabled providers from `GET /auth/providers`.

Register the redirect URIs with your 42 application and Google **Web application** OAuth client. These are the URIs for the ports in `.env.example`. If Google OAuth is in testing mode, add the Google account you plan to use as a test user.

| Provider | Redirect URI |
| --- | --- |
| 42 | `http://localhost:4567/auth/marvin/callback` |
| Google | `http://localhost:4567/auth/google_oauth2/callback` |

```sh
make up
```

The auth service returns JSON and provider redirects. In the same browser session, request `GET /auth/providers`, then post its `csrfToken` as the form field `authenticity_token` to `/auth/marvin` or `/auth/google_oauth2`. This redirects the browser to the provider. On success the callback sets the HttpOnly browser proof cookie and returns `code` and `completionUrl`. Within two minutes, post the `code` as a form field to that URL with the browser proof cookie. Spring saves or updates the user in PostgreSQL, issues the HttpOnly access and refresh cookies, and returns the user profile and token expiry as JSON. Repeat sign-ins with the same provider account reuse the database ID.

Run `make up` again after changing `.env`. Use the same browser-facing hostname and scheme in `AUTH_BASE_URL` and `SPRING_PUBLIC_URL` so the browser can carry the login cookie to Spring Boot.

## Backend JWT authentication

Local accounts can register with `POST /api/auth/register` using JSON fields `email`, `username`, `firstName`, `lastName`, and `password`. Log in with `POST /api/auth/login` using `username` and `password`. First obtain a CSRF cookie and header value from `GET /api/auth/csrf`, as for other state-changing endpoints. Registration immediately signs the user in; both endpoints return the existing user and expiry response and set the access and refresh cookies.

Usernames contain 3–30 Unicode letters, decimal digits, or underscores; matching is case-insensitive and Unicode-normalized. Emails are unique ignoring case. Passwords contain 12–128 characters and are stored as Argon2id hashes. Failed logins are limited to five per username and 20 per client IP within 15 minutes, with a 15-minute cooldown. Limits are held in memory and reset when the server restarts; the server uses the direct connection address, not forwarded headers. Linking existing OAuth accounts is not implemented yet.

## Reset a local password

The Docker stack starts Mailpit as a local email inbox at `http://localhost:8025`. The backend sends reset emails to Mailpit instead of external email addresses. When running the backend outside Docker, run a local SMTP server on port 1025 or set `SMTP_HOST` and `SMTP_PORT`.

Obtain a CSRF token from `GET /api/auth/csrf`, then send a JSON object containing `email` to `POST /api/auth/password-reset/request`. The endpoint returns `202` whether the address belongs to a password account or not; requests for the same address are limited to one per minute in memory. A failed mail delivery is logged without exposing the address or token. Open the Mailpit message and submit its `token` with a new `password` as JSON to `POST /api/auth/password-reset/confirm`, using the same CSRF procedure. The link expires after 30 minutes and only the latest link works. A successful reset revokes existing sessions and issues new access and refresh cookies. OAuth-only accounts cannot use this flow.

`PASSWORD_RESET_BASE_URL` sets the frontend link destination and defaults to `http://localhost:3000/reset-password`. The reset UI is not implemented yet. `PASSWORD_RESET_FROM` changes the local sender address; `HYPERTUBE_MAILPIT_PORT` changes the host port for the Mailpit inbox.

Handoff completion creates a `user_sessions` row, sets both credentials as HttpOnly cookies, and returns only user and expiry metadata:

```json
{
  "expiresIn": 600,
  "expiresAt": "<UTC timestamp>",
  "user": { "id": 1, "provider": "google", "providerUserId": "...", "displayName": "...", "email": "..." }
}
```

The backend sets the JWT in the HttpOnly, host-only `hypertube_access` cookie with `Path=/` and `SameSite=Strict`. The browser sends it automatically on matching backend requests; JavaScript cannot read it, and no authentication token appears in the JSON response. The authentication filter reads only this cookie; Bearer headers are not accepted for user authentication. Use the same browser-facing hostname and scheme for sign-in and the API; cross-origin fetch requests also need `credentials: "include"` and an allowed origin. JWTs use HS256 with a dedicated signing key for this single-service backend. They contain `sub`, `sid`, `jti`, `iat`, `exp`, issuer, audience, and access-token type. Signature, algorithm, type, timestamps, issuer, audience, and identifiers are validated. There is no servlet `HttpSession` or `JSESSIONID`.

The temporary HttpOnly `hypertube_login_proof` cookie binds the one-time login handoff code to the browser that completed OAuth. The Ruby callback generates a random proof and sends only its hash to Spring Boot; completion must present the matching proof cookie and code. A leaked handoff code alone cannot sign in another browser. This cookie is scoped to `/api/auth/login-handoffs/complete`, has a 120-second cookie lifetime, and is deleted after successful completion.

Refresh credentials are random 256-bit Base64URL strings. Only SHA-256 hashes are stored in PostgreSQL. The `hypertube_refresh` cookie is HttpOnly, host-only, `SameSite=Strict`, and scoped to `/api/auth`. Secure cookies are enabled by default. The local `.env.example` explicitly sets `AUTH_COOKIE_SECURE=false` for HTTP development; use `true` with HTTPS. Keep `AUTH_JWT_SECRET` stable across restarts and shared by backend instances. Generate at least 32 random bytes with `openssl rand -base64 32`. `AUTH_JWT_ISSUER` defaults to `hypertube` and `AUTH_JWT_AUDIENCE` to `hypertube-api`. The Ruby provider service continues to use its separate `AUTH_SESSION_SECRET`.

| Endpoint | Behavior |
| --- | --- |
| `POST /api/auth/login-handoffs/complete` | Consumes the browser proof and handoff, saves the user, creates an authentication session, and sets access and refresh cookies plus user/expiry JSON in one transaction. |
| `GET /api/auth/me` | Returns the user profile authenticated by the access cookie. |
| `GET /api/auth/csrf` | Sets `XSRF-TOKEN` and returns its `headerName` and `token`. |
| `POST /api/auth/refresh` | Uses the refresh cookie without requiring a valid access token, rotates refresh credentials, and sets fresh access and refresh cookies without extending the session deadline. |
| `POST /api/auth/logout` | Revokes only the current session and clears both credential cookies; returns `204` even when already signed out. A valid access cookie's `sid` takes precedence over a mismatched refresh cookie. |

For all state-changing API requests, retain the cookie from `GET /api/auth/csrf` and send the response's `token` in the `X-XSRF-TOKEN` header. Missing or invalid CSRF headers return `403`; form parameters are not accepted. Only internal handoff creation (protected by its server secret) and handoff completion (protected by its browser proof) are exempt from CSRF checks. The health endpoint remains public. Authentication failures use centralized Problem Detail responses; invalid refresh credentials return `401` and clear both credential cookies.

Access lasts `AUTH_ACCESS_TTL` (default `10m`). A refresh session expires at a fixed `AUTH_REFRESH_TTL` (default `30d`) after login. This timestamp is set once and never extended. Replace the old `AUTH_SLIDING_TTL`, `AUTH_ABSOLUTE_TTL`, and `AUTH_REFRESH_GRACE` settings with `AUTH_REFRESH_TTL`. Every successful refresh replaces the refresh token and sets a new access JWT cookie, while the replacement cookie's lifetime is only the time remaining until the original expiry. Access JWTs are capped at that same deadline.

Refresh rotation looks up and locks the session by its current refresh-token hash, then replaces that hash. Only the current refresh token is accepted; old or unknown tokens return `401` without revoking the session or invalidating its current token. Old hashes are not retained. The client should serialize refresh requests because concurrent uses of one token produce one success and one failure, and failure responses clear the requesting client's credential cookies. There is no sliding deadline or grace window. Ordinary rotation leaves already-issued JWTs valid until their ten-minute expiry; logout invalidates the session's JWTs immediately through a denylist.

The session table has only `id`, `user_id`, `refresh_token_hash`, `expires_at`, and `revoked`. It stores only the current refresh hash; there is no refresh-token history table. Expired refresh credentials require a new login.

A scheduled cleanup runs every `AUTH_CLEANUP_INTERVAL` (default `PT15M`). Each run removes up to 1,000 expired/revoked sessions and 1,000 expired revocation records using `SKIP LOCKED`. Revocation tombstones remain until the fixed session expiry so deleting a revoked session cannot make its JWTs valid again.

Flyway V7 preserves existing users, session IDs, refresh hashes, and the original absolute expiry as `expires_at`. Sessions whose former idle deadline already passed stay revoked. The migration removes sliding/previous-token fields and grace timestamps. V8 drops refresh-token history while preserving current session hashes and deadlines. Applied migrations remain unchanged, and Hibernate validates the resulting schema.

## Verify changes

From the repository root, run the API smoke test and check the frontend.

```sh
(cd server && mvn verify)
(cd client && npm ci && npm run lint && npm run build)
```

The JWT and refresh integration tests run when `TEST_DATABASE_URL` is set. They reset the users, handoffs, and revocation tables between cases and use a controllable clock for expiry tests. Start a disposable PostgreSQL database:

```sh
docker run --rm -d --name hypertube-session-tests -e POSTGRES_PASSWORD=session-tests -p 127.0.0.1:55432:5432 postgres:17-alpine
```

Once it is ready, run the backend suite and remove the test container:

```sh
(cd server && TEST_DATABASE_URL=jdbc:postgresql://localhost:55432/postgres TEST_DATABASE_PASSWORD=session-tests mvn verify)
docker stop hypertube-session-tests
```

`TEST_DATABASE_USER` defaults to `postgres`. Without `TEST_DATABASE_URL`, the PostgreSQL integration tests are skipped and the controller/security tests still run.

With the API running, `curl -fsS http://localhost:8080/api/health` should return `{"status":"UP"}`.
